# OS File System

> so suppose I am in a dir `path\to\dir` and I write an `ls` command, then what happens? what I think: we are in the dir already so we know the inode number of `dir`, we go to that physical location and read info, that info is a table of file names and inode numbers, we show the file names in it

`ls`

resolve command -> get current dir data (current dir inode number) -> read contents (go to physical place of data using inode and read) -> display

Inode table:
maps inode number to physical data block
list of "file system objects" (file, directory, Symlinks/Hard links, Device files)
has info like: file system object type (notice in my own code where I have something similar to inode `src\app\desktop-environment\services\file-system.service.ts` I had to make a distinction between file and folder already and I didn't know about inode at the time, TODO: make dir "files" similar to `public\assets\file-data\about-me.txt` instead of coding dir info in frontend code, currently the dir structure is baked in to the `file-system.service.ts` file, is that a good way for my specific case? Should I have application code in `public` dir too?), ownership and permissions, file size, last access time (atime), last modification time (mtime), and last attribute change time (ctime), hard link count, disk block pointer and a few more
Note: this doesn't contain file names, file names are dir data, a dir file system object has its own data, it is a table of file name and inode number

Directory:
has a table mapping file name and inode, each entry is called directory entry/dentry (look up dentry cache)
